# 场界面：信息怎么摆，接口怎么给

> 结论先行：粒子场不是"另一种画布"，是一台**状态演示器**。它能同时表达 3~5 个连续量、
> 能表达"正在发生"、能表达"变化的方向和速度"，但表达不了精确读数和大批量枚举。
> 所以接口不该是"把渲染树翻译成点"，而是**三个语义动词 + 一小套场词汇**，
> 几何全部由前端解算。

---

## 1. 场里到底有哪些"可写通道"

一个 6400 点的场，可控的连续量只有 9 个。所有信息都必须落到其中之一 ——
这是设计的天花板，也是它和 DOM 最根本的区别（DOM 的通道是"位置 + 尺寸 + 样式"，离散且互相独立）。

| # | 通道 | 范围 | 感知特点 |
|---|---|---|---|
| 1 | 分布（点云形状） | 任意 2D 形状 | 一眼看出"是什么"，但慢 |
| 2 | 相干度（抖动幅度 / 方向一致性） | 0 = 散乱，1 = 刀切般整齐 | 极快，接近本能 |
| 3 | 亮度 / 密度 | 0..1 | 快，但受体量影响 |
| 4 | 流向（速度场方向） | 角度 | 快，且天然带"意图" |
| 5 | 速度（流速） | 0..N px/s | 表达速率最自然 |
| 6 | 相位（脉动节律） | 周期 + 相位差 | 适合"同类/同步" |
| 7 | 余晖（拖尾长度） | 0..1s | 唯一的"历史"通道 |
| 8 | 势阱（吸引子） | 位置 + 强度 | 定义"注意力在哪" |
| 9 | 沉积（永久落点） | 位置 + 数量 | 唯一的"可累积"通道 |

**关键区分**：1、8、9 是"空间"的；2~7 是"时间"的。
DOM 只有空间，所以它必须靠"再画一个元素"来表达变化；场可以直接改时间参数，**粒子数不变**。

---

## 2. 编码器：语义 → 通道

九个语义类型，各自绑一个主通道 + 一个辅通道（辅通道用于同一量的第二种编码，互为校验）。

| 语义 | 例 | 主通道 | 辅通道 | 为什么这么配 |
|---|---|---|---|---|
| 标量 0..1 | CPU 71% | **沉积量** | 数字（凝聚成字） | 面积可比、可同时看多个；数字给精确值 |
| 速率 | 2.1 MB/s | **流速** | 亮度 | 速度本身就在表达速率 |
| 等级 / 健康度 | 正常·注意·危险 | **相干度** | 湍流（局部） | "乱 = 危险"，接近本能判断 |
| 类别 | 3 个服务 | **流向角度** | 色带 | 空间分组，省掉图例 |
| 时间序列 | 7 天趋势 | **余晖** | 沉积层 | 历史留在场里，不用另画折线 |
| 事件 | 报错 / 完成 | **冲量** | 相位对齐 | 事件是瞬时的，冲量也是 |
| 关系 | A 依赖 B | **两团之间的流** | 同相位 | 连接本身可以动，DOM 只能画线 |
| 归属 | 4 个文件同一批 | **同势阱** | 同相位 | 同步脉动 = 同类，不需要边框 |
| 存在 / 消失 | 任务在跑 → 结束 | **相干 ⇄ 溶解** | — | 存在感是连续的，不是"有/无" |

**反例（不要这么用）**：用点云形状画柱状图 —— 那是把场的第 1 通道当柱子的高度用，
既慢又占预算，还比不上一个真图表。柱状图属于 DOM，不属于场。

## 3. 构图：三层注意力，四个固定位

场装不下"一屏信息"，但能装下**一屏注意力**。所以按注意力分层，而不是按内容分区：

- **L0 场层（始终可见）**：1~4 个标量或事件，占全局。回答"现在怎么样"。
- **L1 结构层（同时在场的对象）**：≤7 个，按极坐标摆开（角度=类别，半径=重要度）。
  回答"有哪几件事，它们什么关系"。
- **L2 细节层（一次只开一个）**：把焦点那团粒子凝聚成文字/数字。其余对象压缩成"团"。
  回答"这件事到底多少"。

三层是**同一批粒子的三种相干模式**，切换靠相变（溶解 → 重组 → 凝聚），不是叠两层 UI。
这就是粒子世界的"缩放"：不是放大倍率，是相干度。

**四个固定位**（不要每次重新发明构图）：

| 位置 | 语义 | 常驻内容 |
|---|---|---|
| 中心 | 当前焦点 | L2 细节 / 正在进行的任务 |
| 环（极坐标） | 其他对象 | L1 结构层 |
| 底部横带 | 时间轴 / 进度 | 沉积带、尾迹 |
| 边缘 | 异常 | 局部湍流（越严重越靠内、越抖） |

## 4. 接口：四个动词 + 一套词汇

### 4.1 设计原则

1. **模型说语义，不说几何。** 不给坐标、不给点数、不给字号 —— 和"不让模型算像素"同一条纪律。
2. **持续态和瞬时事件分开。** `set` 幂等可覆盖，`pulse` 一次性。混在一起会让场永远在抖。
3. **一次只给一个景（scene）。** 不是给一堆独立组件，前端才有权决定构图。
4. **几何参数留在代码里。** 模型的输出越"胖"，调参就越要改提示词；这里反着来。
5. **换景是相变，不是切页。** 换一屏别"先清空再画"，那是两次重排；把相干度压到 0 再抬回来，
   同一批粒子换一个形状 —— 代价一次，过程还自带意义（"旧的不成立了 → 新的在成形"）。

### 4.2 工具

```jsonc
// 1) 布景：幂等，整场替换（带 rev 做增量）
scene_set({
  "rev": 7,
  "focus": "job",                    // 哪个对象进中心（L2）
  "layers": [ /* 见 4.3 */ ],
  "mood": "calm"                     // calm | alert | working —— 全局相干度基调
})

// 2) 推进：只改数值，不重排（进度、指标刷新走这个）
scene_patch({ "rev": 8, "ops": [
  { "id": "job",  "progress": 0.72 },
  { "id": "cpu",  "value": 0.45 }
]})

// 3) 事件：一次物理动作，前端翻译成冲量/相位/湍流
scene_pulse({ "kind": "confirm", "at": "job", "intensity": 0.7 })

// 4) 换景：溶解 → 换几何 → 重组（不是淡入淡出）
scene_transition({ "rev": 9, "focus": "load", "layers": [ /* 新的一屏 */ ] })
```

`scene_transition` 和 `scene_set` 的 spec 完全一样 —— 差别只在"要不要过程"。第一屏用 `set`
（直接成形），之后的换景都用 `transition`。

时长不用传：`outMs` / `inMs` 的缺省值来自 `timing.js`（360 / 780），模型改它没有意义 ——
时序是前端的事（见 §7）。

`scene_pulse.kind` 只有四个，映射固定：

| kind | 物理动作 | 用在哪 |
|---|---|---|
| `confirm` | 全场相位对齐一次（一次心跳） | 用户确认、任务提交 |
| `arrive` | 一束流从边缘汇入焦点 | 数据回来、下载完成 |
| `error` | 局部湍流 + 相干度骤降 | 失败、越限 |
| `settle` | 焦点沉积一层、其余变暗 | 阶段完成、收尾 |

**反方向也有一条通道：手势意图。** 用户拖了/点了什么，不是一条工具调用，而是一条**入站消息**，
和用户说的一句话等价：

```jsonc
{ "role": "intent", "kind": "adjust", "target": "mem",
  "label": "内存", "from": 0.60, "to": 0.34, "delta": -0.26 }
```

模型对它的处理和对一句话完全一样：可以直接执行、可以反问、可以说"这个做不到，因为……"。
唯一的区别是它**天然带着结构**（哪个对象、从多少到多少），所以模型不必先猜"用户指的是什么"。
细节见 §8。

### 4.3 场元素（layer）

六种，各自对应一个编码器。字段只有语义，没有几何。

```jsonc
{ "id": "cpu",    "kind": "gauge",      "label": "CPU",   "value": 0.71, "trend": "up" }
{ "id": "mem",    "kind": "gauge",      "label": "内存",  "value": 0.60 }
{ "id": "job",    "kind": "stream",     "label": "追剧",  "progress": 0.62, "rate": "2.1 MB/s" }
{ "id": "n8n",    "kind": "turbulence", "label": "n8n",   "level": 0.35 }
{ "id": "choice", "kind": "fork",       "label": "要归档吗",
  "options": [ { "id": "yes", "label": "归档 4 个" }, { "id": "no", "label": "先看看" } ] }
{ "id": "note",   "kind": "condense",   "text": "内存最低还剩 3.1 GB" }
```

| kind | 渲染成 | 交互 |
|---|---|---|
| `gauge` | 一段弧的沉积量 + 随 value 变快的脉动 | 悬停吸附、数字浮现 |
| `stream` | 从源到目标的流 + 已沉积的段 | 点它 → 成为 `focus` |
| `turbulence` | 局部抖动，level 越高越乱、越靠近中心 | 点它 → 展开原因（可能是 condense） |
| `fork` | 两股流向两侧分叉，光标是第三个吸引子 | 光标靠近哪股，那股被拉过来；点 → pulse(confirm) |
| `condense` | 粒子凝聚成一行字 | 无（纯读数） |
| `trace` | 一条曲线 + 一个来回扫的头；**新旧靠亮度编码** | 点它 → 成为 `focus`（给峰值/区间读数） |

### 4.4 谁该走场，谁该走渲染树

| 内容 | 通道 | 理由 |
|---|---|---|
| 3~5 个指标同时在场、要比较 | **场（gauge）** | 一个屏幕内的相对大小，场比数字快 |
| 一个任务的进行感 | **场（stream）** | "到哪了"是空间感，不是数字 |
| 等待 / 卡住 / 出错 | **场（turbulence）** | 状态本身该被感知，不该只出现在日志里 |
| 二选一、要不要继续 | **场（fork）** | 选择是两个方向，不是一个按钮 |
| 表格、列表、代码、表单 | **渲染树（DOM）** | 要读、要选、要复制、要精确输入 |
| 精确数字 | **两者叠加** | 场给"多少"，字给"几" |
| 历史明细 | **两者叠加** | 场给趋势（尾迹），表给数据点 |

规则一句话：**"要看一眼就知道"的走场，"要读进去"的走 DOM。**

## 5. 失败模式（这些是硬边界）

1. **精确读数**：场分不清 71% 和 71.3%。→ 必须叠数字。
2. **枚举上限**：L1 同时在场超过 7 个就糊成一片光。→ 分组 + 只开一个 focus。
3. **动画税**：每次状态变化要 200~800ms 才被感知。连续高频更新（比如每秒 10 次的指标）必须节流到 2~5Hz，否则场永远在半路上，看着像故障。
4. **对比度**：相干度差异在低端屏 / 强光下会丢失。→ 相干度至少配一个亮度的辅编码。
5. **无障碍**：视觉全是点，读屏软件读不到。→ 必须有一个同步的 `aria-live` 文本层说出同样的内容（§6.5 已实现；这是 DOM 的职责，不是妥协）。
6. **"看着累"**：长时间盯着持续运动的画面会疲劳。→ 空闲时必须降到很低的能量（呼吸幅度小、频率低），静息功耗要能调。

## 6. 实现状态

| 项 | 状态 | 位置 |
|---|---|---|
| 场的三个原语（势阱 / 冲量 / 出生点） | ✅ | `field.js` |
| 字模缓存 + 固定槽位（就地凝结） | ✅ | `pui.js` |
| `gauge` / `stream` / `fork` / `turbulence` / `condense` | ✅ | `scene.js` |
| `trace`（曲线 + 扫掠头 + 自适应标度） | ✅ | `scene.js` |
| `set` / `patch` / `pulse` / `transition` 四个方法 | ✅ | `scene.js`（与工具 1:1 对应） |
| 相变换页（溶解 → 重组） | ✅ | `scene.js` + `field.js` 的相干度 |
| `aria-live` 同步层（镜像摘要 + 节流 + 事件通道） | ✅ | `aria.js` |
| 时序规范 + 节拍器（`brief()` 进提示词，`Pacer` 强制间隔） | ✅ | `timing.js` |
| 手势 → 意图（拖值 / 平移窗口 / 点击下钻 / 选择） | ✅ | `gesture.js` + `scene.js` 的 `hot` |
| 视图复位（`resetWin`）、结论过期（`ghost`） | ✅ | `scene.js` |
| 服务端 `scene_*` 工具与审计、意图回灌通道 | ⬜ | 随 M0 |

**可播放的规格**：`shell/demo.html`（`node tools/dev/serve-dir.mjs shell 8766` → `/demo.html`）。
20 秒里把 `set / patch / pulse / transition` 各走一遍，左下角同步打出每一步的工具名与参数 ——
它既是演示，也是"这套接口读起来是什么样"的样本。`?stop=11.4` 停在某一秒。

**一屏实测**：3 个 gauge + 1 条 stream + 1 个 fork + 1 团 turbulence = **5482 / 6400 槽位**
（加一行常驻提问字幕 560 → 6042）。
这基本就是这套构图的上限，再加东西就得砍一种 kind。

#### 6.1 实现时踩到的四个坑

1. **槽位越界不会报错，只会静默覆盖邻居。** stream 的流动段原来按 `N×0.45` 预留，但 `flowN = N - depN`
   在进度变大时会超过预留，直接盖掉了后面标签的槽位 —— 症状是"标签凭空少了一半字"。
   现在一律按 `N` 预留，且**分配和写入必须同一个数**。
2. **场的文字必须短。** 超过 10~12 个汉字就得截断，截断后语义就废了。所以 layer 的 `label` 是"标签"不是"句子"，
   句子交给 `condense`（一行、居中、最多 20 字）。
3. **`dim` 色的字在点阵里几乎看不见。** 16px 的字用亮度 0.56 的颜色，点又小又稀，肉眼直接丢失。
   标签要提到 `#93b8d8` 这个档（对应亮度 0.78 左右）。
4. **锚点决定"读数挂在哪"。** 细节读数如果挂在流的左端，看起来像孤立的字；挂在中间才像这个流的一部分。

#### 6.2 `patch` 不重排的证据

`docs/images/scene-progress-strip.png` 是 18% / 62% / 93% 三帧：只有沉积段的长度在长，
三个仪表的环、分叉的两股流、所有文字一个像素都没动。这正是固定槽位 + 字模缓存带来的性质 ——
换句话说，**"进度推进"在这个系统里是"多沉积几颗"，而不是"重画一遍"。**

#### 6.3 相变换页：溶解 → 重组

DOM 的换页是**两个状态层交叉淡入淡出**：旧的一层在退场、新的一层已就位，中间有一段"两个界面同时可点"
的混乱期，还得处理"旧的还没走完新的就来了"。场里没有这件事 —— 换景只有三步：

```
相干度 1 → 0     目标被每点固定的噪声方向推开（位移 ∝ (1-coh) × 40px），结构自己塌掉
换几何            set(新 spec)，此时 coh = 0，新形状直接以"散开的云"出现
相干度 0 → 1     目标重新可信，结构自己长回来
```

`field.js` 里只有一个开关：`setCoherence(k)`。它对每颗点做的事是：

```js
tx = drawX[i] + jit[i*2]   * (1 - coh) * 40;   // jit 是每点固定的随机单位向量
ty = drawY[i] + jit[i*2+1] * (1 - coh) * 40;
sa = drawA[i] * drawMix * rev * (0.35 + 0.65 * coh);
```

**jit 必须是"每点固定"而不是"每帧随机"。** 每帧随机出来的是闪烁（雪花屏），固定下来才是"这团东西
失去了形状"。这是同一句话的两种实现，观感差一个量级。

**时间**：溶解 380ms（`k²` 缓入，越散越快），重组 760ms（`1-(1-k)³` 缓出），总共约 1.15s。
比 DOM 的 300ms 慢，但这是**换一整屏的内容**，而且过程本身携带信息（"旧的已经不成立了"）。

**必须提刚度，并且不能衰减回 1。** 换几何后点要走的路程比平时大得多（实测平均重排距离 ~500px，
因为两个景完全没有共用的位置）。干刚度 46 要走 1.2s 才落定，而相干度 760ms 就回 1 了 ——
结果是"已经宣布成形，但字形还在抖"。

第一版把刚度写成 `1 + 1.6 × (1 - k)`，随相干度一起衰减回 1，正好在**收尾最需要硬的时候变软**：
实测平均位置误差停在 **6px**，而点距才 2.4px，画面上就是一层毛边。改成恒定 2.4 之后误差降到 4.7px
且继续收敛，重组末尾能干净落定。

**可被打断**：`transition` 在运行时再来一次，会从**当前相干度**重新算溶解时长（`outMs × coh`），
不会先"补满"再溶。自检（`?selftest=1`）连打三次 B→A→B：终态 `coh=1 / stiff=1 / busy=false / rev` 正确、
槽位无泄漏。

`docs/images/phase-strip.png` 是同一场相变在 0 / 120 / 260 / 420 / 800ms 和终态的六帧。

#### 6.4 `trace`：时间用亮度编码，不占槽位

DOM 画一条时间序列 = 折线 + 轴 + 网格 + 高亮段。场里只要三样东西：

| 元素 | 编码了什么 | 成本 |
|---|---|---|
| 曲线（280 颗点） | 数值本身 | 280 槽位 |
| **亮度**（左暗右亮） | **时间**：越新越亮 | 0（不额外占槽位） |
| 扫掠头（来回走的高光，且抬高 3.5px） | "现在"以及"这个东西是活的" | 0（逐帧改 drawA） |
| 地平线（72 颗极暗的点） | "零"在哪 | 72 槽位 |

这就是"历史免费留在场里"的实证：**时间这个维度没有占任何额外槽位，它就是亮度**。

**自适应标度是必须的。** 一屏的负载数据落在 0.14~0.56，铺在 0~1 的格子里就永远贴着地平线 ——
第一版看起来像"一条划痕"。现在缺省取 `峰值 × 1.2` 向上取到 0.1 的整数倍；要绝对标度就传 `axis:[0,1]`，
那是语义（"这是百分比负载"），该由模型说。

副作用要认：自适应意味着**来一个新高点时整条曲线会重新标度**（全局重映射）。语义上说得通
（"这个尺度装不下新数据了"），但要稳定可比就必须显式传 `axis`。

**`patch` 换数据只改目标，不重画。** `_tracePoints` 把新数据重采样成 N 个 y，写进同一批槽位；
曲线滑过去是弹簧干的活，没有任何逐点 FLIP。`docs/images/trace-morph-strip.png` 是原来 / +90ms /
+260ms / +600ms 四帧：整条曲线带惯性抬升，落定后是新的形状。

一屏实测（`?scene=b`）：曲线 280 + 地平线 72 + 标签/读数/两个仪表的文字 = **3160 / 6400 槽位**。

**一个硬约束**：`trace` 和 `stream` 共用流区，一个场景只能放一个；两个 `trace` 会重叠 ——
多序列要么叠成一条带区间的线，要么换场景。

#### 6.5 `aria-live` 镜像层：这件事反过来约束了接口

场里没有一个字是真 DOM，读屏软件看到的是空白。所以每场景必须镜像一份**语义摘要**。

有意思的是：**这一层要求 spec 必须是语义的**。如果给模型的 spec 里只有几何（角度、半径、点数），
就没法生成一句人话。能翻译成"服务器状态。CPU 71%。内存 60%。……需要选择：要处理 n8n 重启吗。
选项：重启 n8n、先看着。n8n 重启 程度 40%。正在处理" —— 这本身就是"模型只说语义"这条纪律的检验。

两个通道：

| 通道 | 属性 | 用在哪 | 节流 |
|---|---|---|---|
| 状态 | `role=status` / `aria-live=polite` / `aria-atomic` | `set` / `patch` / 相变完成 | 2.4s，且**延后补播最后一次** |
| 事件 | `role=alert` / `aria-live=assertive` | `pulse(confirm/arrive/error/settle)` | 不节流（一次事件一句话） |

**节流必须带尾部补播**：进度每 400ms 推一次，如果只在"到点"时播，读屏用户永远听到中间值。
现在的做法是"排一个定时器，停下后播最终状态"。实测 10 次连续 `patch` → 只播 1 次。

**同样的文字不会被重播**（读屏只看内容是否变化），所以重复时要先清空再写（下一帧补回）。

配套的还有两条：粒子 canvas 标 `aria-hidden="true"`（它本身对可访问性树无意义），
镜像层用 `clip-path` 隐藏而**不是** `display:none`（后者会把它从可访问性树里摘掉）。

---

#### 6.6 还剩什么

1. **`trace` 的峰值标注**：现在只说"当前 18%"，看不懂"周四那个尖峰是多少"。需要按 `focus` 给一个峰值读数。
2. **相变的"中途反悔"体验**：技术上能打断，但观感上是"散到一半又聚回来"，还没有专门的观感验证。
3. **`condense` 与相变的关系**：换景时最后一行结论是先溶掉再出现，还是跟着一起走，没定。
4. **人手验收**（静态图看不出来的）：`confirm` 的相位对齐能不能被"看出来"；`fork` 的光标吸引像不像"选"。

已用 `shell/test-scene.html` 验证了 1~3 的一半：三个 gauge 的环一眼可比、stream 的沉积段能看出"到哪了"、
fork 的两股流带标签能读懂、相变六帧成立、曲线滑移成立、aria 摘要可读。

## 7. 时序：动效该多长，以及两步之间空多久

### 7.1 上一版错在哪

20 秒的演示，每一步都被说"有点短，不够人反应"。查下来不是某一处慢，而是**只算了动效本身多长，没算人看完它需要多久**：

| 动作 | 动效时长 | 到下一步的间隔 | 问题 |
|---|---|---|---|
| `scene_set` 铺开一屏 | ~900ms | 1.7s 后提问散开 | 勉强 |
| `patch` 进度推进 | ~240ms | 1.1s | 偏挤 |
| `pulse(error)` 抖起来 | ~600ms | 1.8s 后换景 | 挤 |
| `scene_transition` 换整屏 | ~1.1s | 3.2s | 可以 |

所以时序要拆成**两个数**，而不是一个：

```
DUR   这个动效持续多久（前端固定，模型不能调）
GAP   它结束之后，至少空多久才允许下一个叙事动作
```

### 7.2 两半的数值

`DUR`（`timing.js` 的 `TIMING`）：

| 档 | 时长 | 用于 | 依据 |
|---|---|---|---|
| `TAP` | 60ms | 触碰反馈、按下回弹 | 超过 100ms 就被感知为"卡" |
| `HOVER` | 140ms | 势阱建立 | 要"立刻有反应"，但完全瞬时反而像抖 |
| `TICK` | 240ms | 数值推进 | 一格里看得清"变了多少"的最短时间 |
| `STEP` | 380ms | 单元素换状态 | 一个仪表从正常变注意 |
| `ENTER` | 900ms | 新内容登台 | 短于 700 像"闪现"，看不出成形过程 |
| `SWAP` | 360 出 + 780 入 = 1140ms | 换整屏 | 两段观感是两件事，必须分开给 |
| `LOOP` | 2600ms | 呼吸、扫掠头 | 慢于注意力节律才不抢戏 |

`GAP`（两步之间）：

| 上一步 | 至少停 | 依据 |
|---|---|---|
| `patch` | 200ms | 数值可以连着来，但要留出"看清这一格" |
| `pulse` | 560ms | 一次物理事件，得先让人注意到它发生过 |
| `set` | 900ms | 一整屏铺开，扫一眼的时间 |
| `transition` | 1100ms | 人还在确认"刚才那屏没了" |
| `condense` | 1600ms | 按 4 字/秒读完 20 个字 |

### 7.3 一条硬下界：动效不能短于物理

`DUR` 不是随便定的，它有一个下界来自场本身：**位置是弹簧积分出来的。**

```
刚度 46（默认）    跨屏位移落定 ~1200ms
刚度 2.4×（相变重组）   ~500ms
```

所以想"快一点"**只有一条路：提刚度**。把时间轴调短只会让点"没走到位就被宣布成形"——画面上是毛边，不是快。这条写成给模型的规矩：

> 想快只有一条路：提刚度，不是缩时间。

### 7.4 时序必须由前端强制，不能只写提示词

`timing.js` 的 `brief()` 会输出一段可以直接进系统提示词的规范。但**规范只解决"有没有正确直觉"，解决不了"会不会遵守"**：模型看不到时钟，也不会数"上一步之后过了 400ms"。所以真正的间隔由 `Pacer` 保证：

```js
pacer.run('transition', () => scene.transition(spec));
pacer.run('patch', () => scene.patch(ops));   // 排队，等上一个的 GAP 走完
```

实测连发四个动作（`window.__burst()`）：

```
set@0ms  →  pulse@914ms  →  patch@1493ms  →  transition@2600ms
```

一次调用里连发四个，前端把它们拉成 2.6 秒的节奏。队列里同 kind 的会合并（只保留最后一次），所以"弱模型连推 5 次进度"不会变成 5 次抖动。

**分界**：用户手势引起的反馈**不进队列**（延迟 300ms 就不是直接操作了）；只有模型发起的叙事动作才排队。

### 7.5 违反时会怎样（三种可识别的症状）

| 症状 | 原因 |
|---|---|
| "看了但什么都没记住" | 两个动效挤在一起，第二个盖掉第一个 |
| "不想看下去了" | 连续换景，人跟不上，索性放弃 |
| "边缘毛糙、像没渲染完" | 动效短于物理落定（§7.3） |

## 8. 手势：产生意图，不产生动作

这是把"鼠标被粒子吸引"升级成"鼠标在表达意思"的那一层（`shell/src/gesture.js`）。

### 8.1 一句话原则

> **手势从不执行动作，只产生意图。**

拖内存往下，不代表"把内存清掉"，而代表"我想让内存低一点"。中间那一步（要不要做、能不能做、怎么做）必须由模型接住。这条分界线同时是三件事：

- **安全**：拖拽永远不能直接等于一次破坏性操作
- **语义**：模型有上下文（现在 60%、下面是 n8n 占的），它才知道拖到 34% 可行不可行
- **观感**：反转确认（模型反问）比"拖了就变"更像在和一个懂你的东西打交道

### 8.2 三种手势，靠方向区分

锚点长在元素自己身上，所以**不需要额外的把手**：拖离它是"改值"，沿它拖过去是"改窗口"。

| 手势 | 判据 | 意图 | 谁执行 |
|---|---|---|---|
| 纵向拖 | `|dy| ≥ |dx|` | `adjust` `{from, to, delta}` | **模型**（要反问、要算代价） |
| 横向拖 | `|dx| > 1.35·|dy|` | `pan` `{dir, dx}` | **本地**（视图操作，见 §8.4） |
| 几乎不动就松手 | 位移 < 9px 或 < 110ms | `tap` / `pick` | 模型（下钻 / 选择） |

`1.35` 的不对称系数是故意的：斜着拖的时候，人心里想的通常是纵向（"把它拉下来"），横向要多明显才算数。

### 8.3 意图是"几号到几号"，不是"一点增量"

```jsonc
// 拖完之后交给模型的，是这个 —— 不是屏幕坐标
{ "kind": "adjust", "target": "mem", "label": "内存",
  "from": 0.60, "to": 0.34, "delta": -0.26 }
```

模型拿到 `from/to` 才知道要不要问"压到 34%？"、能不能做到、代价多大。只给 `delta: -0.26` 它得自己反推当前值，只给坐标它就什么都不知道。**手势的产物必须是语义，不是坐标。**

配套一条：任何一次拖拽都要能被复述成一句人话（`describe()`）：

```
把「内存」从 60% 拖到 34%
把「CPU · 3 天」往回翻页
在「卡在 Notion 节点？」选了「先禁用它」
```

复述不出来，说明这个手势的设计有问题。

### 8.4 分界线：可以本地改视图，不能本地改事实

这是整套交互里最要紧的一条判据：

| 动作 | 性质 | 处理 |
|---|---|---|
| 平移折线的观察窗口 | **视图**：改的是"看哪一段" | 本地立即执行 |
| 拖仪表的值 | **事实**：改的是"内存占用是多少" | 只产生意图，等模型确认 |
| 拖进度条 | **事实**：进度是"跑了 62%"，拖它等于让界面说谎 | 不提供该手势（`stream` 只声明 `tap`） |
| 双击折线复位窗口 | **视图** | 本地立即执行 |

元素自己声明接受哪些手势（`layer.hot.gestures`），不是全局配置：

```js
gauge      → ['adjust']
trace      → ['pan']
stream     → ['tap']        // 故意不给 seek
fork 分支  → ['pick']
turbulence → ['tap']
```

所以"这个元素能不能拖"是编码器在布局时决定的事，模型无从要求 —— 和几何不交给模型是同一条纪律。

### 8.5 决策槽是排他的

场里只有一个"决策槽"。用户拖了内存、模型反问"压到 34%？"，这个问句**占据**那个位置；如果此时又来一个问题，就把旧的就地换掉，而不是新建一个。

理由不是省槽位，是**人一次只能回答一个问题**。屏幕上同时挂两个待答的问题，一个都不会被回答。技术上靠 `patch` 换 `fork` 的文案实现（零重排，几何不动）：

```js
scene.patch([{ id: 'choice', label: '把内存压到 34%？',
               options: [{id:'yes',label:'压到 34%'},{id:'no',label:'算了'}] }]);
```

做完之后，同一个槽换成"结果 + 撤销"——"我刚做的事"和"我刚被问的事"是同一个位置上的两件事。

### 8.6 视图变了，结论就过期了

折线被平移之后，屏幕上那条"周四 21:00 有一次尖峰"就**不再成立**（周四已经不在视野里）。三种处理都不对：本地改写结论（那是模型的话）、直接删掉（人会以为结论凭空消失）、不动（界面在说谎）。

正确做法是 `scene.ghost(id, true)`：把它淡到 30%，让它读作"这属于上一段视角"。等模型给出新结论再替换。这也是唯一一处"界面主动承认自己过时"的地方。

### 8.7 实现时踩到四个坑

1. **命中测试不能用"离锚点多远"。** 折线的锚点在标题处，曲线上根本点不到；分叉的两个分支共用一个锚点，永远分不出点了哪边。必须由每个编码器在布局时写下 `hot`（圆形或矩形 + 接受的手势）。
2. **`up()` 里先把 `this.g` 清空再算快照，`axis` 永远是 null。** 症状很隐蔽：拖动过程中一切正常（窗口在动），松手后什么都不发生，**不报错**。快照必须在清空前算。
3. **灵敏度不能用控件尺寸。** 纵向 140px 走完一个量程（仪表直径 104 的 1.3 倍）时，"往下拖一点点就到底"。判据：**走完整量程的物理距离应该是控件尺寸的 2~3 倍**，所以取 240px。
4. **槽位写入必须"写满或清空"。** 一个字的点远少于它预占的槽位段，新字比旧字点少时，旧字的残余点会留在原地 —— 症状是改一行字之后，新字中间浮出几个旧字笔画（`把内存压到 34%？` 里透出 `n8n 重启`）。不会报错，只会被当成渲染抖动。

### 8.8 一条完整的链路（实测日志）

```
› 用户   把「内存」从 60% 拖到 34%          +0.3s
intent   adjust mem 0.60→0.34
scene_patch  choice 换成「把内存压到 34%？」
› 用户   在「把内存压到 34%？」选了「压到 34%」
intent   pick choice.yes
scene_patch  mem.value → 0.34
fs_free  已压到 34% · 释放 2.4 GB
```

模型只收到两句话（一次 `adjust`、一次 `pick`），中间那个反问是它自己的决定。**用户看见的是"它懂了"，模型看到的是一条意图。**

## 9. 接口要按模型能力分层（2026-10-21 实测）

前面那套「四个动词 + 六个编码器」是**给强模型**的接口。真正接上免费模型之后，
它暴露出一个不是措辞、而是**层级**的问题。

### 9.1 实测：四个免费模型，四种坏法

同一个提示词、同一句「机器怎么有点卡」，各跑三轮：

| 模型 | 延迟/步 | 表现 | 坏在哪 |
|---|---|---|---|
| Qwen2.5-7B | 0.9s | 会调工具、会铺屏，但常补一段旁白，偶尔完全不铺 | 指令跟随弱 |
| Qwen3.5-4B | 15s | 三步走完（sys_status → app_list → scene_show），数字真实 | 慢；收尾会重复一次 |
| Qwen3.5-9B | 6s | 一次跑完、一次只调了一个工具就停 | 不稳定 |
| GLM-4-9B | 0.5s | 只看数据，然后写一段长解释，不铺屏 | 不理解"输出是一屏" |
| Xing-29B | 2s | 结构对，但把 `ask` 写成一个字符串；有一次把工具调用写成 `<tool_call>` 文本 | 参数与通道不可靠 |

共同点很清楚：**它们都能"看"，但都不可靠地"画"。**

### 9.2 结论：不能把"一屏怎么长"交给模型

六个编码器 + 每层唯一的 id + 每层各自的字段，是**同时**要求模型做三件事：
选对编码器、起对 id、填对字段。7B~29B 级模型一次做对三件的概率很低，
而且失败是**静默**的（少一个仪表，界面上看不出是谁的错）。

所以接口分两层：

```
高层（默认）  scene_show { reading, gauges[], note, ask, yes, no }
              字段全平、全部可选、不用 id、不用 kind
                     ↓ 服务端展开（expandShow）
底层（需要精确控制时）  scene_set(spec) / scene_patch(ops) / scene_ask / scene_pulse
              六个编码器，每一层自己写 id
```

三条经验，都是反直觉的：

1. **嵌套字段是模型的敌人。** `ask: {label, yes, no}` 被四个模型里的三个写错
   （写成字符串、只写 label、写成数组）。改成三个平铺字段 `ask / yes / no`
   之后一次就对。**每多一层嵌套，就多一次出错的机会。**
2. **"要说的话"也要走参数。** `reading` 让模型在一个有长度约束的字段里写那一行，
   比让它写自由文本 `content` 可靠得多 —— 后者七成会写成一段带换行的解释。
3. **旁白要咽掉。** 模型爱说"调 app_list 看看""当前系统状态如下：""请调用 scene_ask"。
   这些是**它对自己的指令**，不是给用户的话。服务端按工具名/复述句式过滤掉，
   否则场里那一行会被旁白占满。

### 9.3 兜底：模型不画，系统画

即使有了高层动词，仍有回合里模型看完数据就停了，什么都铺不出来。
这种情况由系统自己铺 —— `defaultOverview()` 用刚取到的读数拼出
"三个仪表 + 一行读数 + 一个可选的问题"。

这不是"替模型作弊"，是承认一件事：**一屏的基本形状是系统的 affordance。**
和"几何不给模型"是同一条原则 —— 用户问"机器怎么卡"，屏幕上至少要有读数，
这不该取决于这次采样模型有没有想起来铺屏。模型想表达更多时，它自己调 scene_show 覆盖。

### 9.4 两条规则从提示词搬进了代码

| 规则 | 原来靠 | 现在 |
|---|---|---|
| 一手势 `adjust` 不能直接执行 | 提示词说"这是意图不是命令" | 该回合内 `danger` 工具**直接拒绝**并回一句解释 |
| 铺过屏 / 问过问题就停 | 提示词说"不要重复铺" | 整屏判重 + 每轮最多两屏 + 手势回合画完即 `break` |

理由和几何、时序一样：**它们不该随模型好坏而变。** 提示词是给模型"正确的直觉"，
代码是保证"错的时候也不会出丑"。实测里模型在被拒绝后确实会补一个 `scene_ask`，
说明"拒绝 + 说明原因"比"求它别这么做"有效。

## 10. 接上真集群之后（2026-10-21）

前面所有关于"场"的设计都在假数据上成立。接上那台真在跑的 Olares（单节点 k3s，
15.6 GB 内存，12 个用户命名空间的 pod）之后，有三件事是**只有真数据才会暴露**的。

### 10.1 数据从哪来：一条 TLS 通路

不调 `kubectl`，用 `node:https` 直连 k8s API（6443）。关键是 **API 的 service proxy**：

```
/api/v1/namespaces/kubesphere-monitoring-system/services/prometheus-k8s:9090/proxy/api/v1/query
```

一个端点同时拿到 k8s 对象和 Prometheus 的时间序列，不用 port-forward、不用暴露 ClusterIP。
同一份代码在本机（kubeconfig + 公网 6443）和集群内（serviceaccount）都能跑。

一个必须记下来的实测：**这个集群没有 metrics-server**，`kubectl top nodes` 直接报
`Metrics API not available`。但 Prometheus 一直在采 `container_memory_working_set_bytes`——
所以"谁在吃内存"这个问题有答案，只是不能走 `top` 那条路。

### 10.2 真曲线让"标度"变成了道德问题

`trace` 原来用自适应标度（窗口内峰值的 1.2 倍）。在 mock 数据上这是对的：手写的曲线
本来就是为了好看。但在真数据上它是**撒谎** —— 内存从 40% 到 41%，自适应会把这一点点
波动画得像剧烈震荡，用户看到的是"出事了"。

所以真实指标一律传 `axis: [0, 1]`：**曲线的高度就是百分比本身**，和旁边三个仪表能对上。
平就是平。这是真数据带来的一条新规则 —— **标度不是审美选择，是语义**。

同时补了峰值标注（`峰68%`）：真曲线才有"这一小时最高到这"这个信息。
原来没做是因为标在自己编的数上没有意义。

### 10.3 单位会骗人：382 MB 被当成 0.382

最危险的一处，也是最容易漏的。

`app_list` 返回 `memMB: 382`。模型要把它塞进 `gauge.value`（0~1 的比例），于是它
**自己除了个 1000**，给出 `0.382`。屏幕上显示 38%，而 n8n 实际占 2.4%（382MB / 15.6GB）。

这个错误**不会报任何错**：值在合法范围内、仪表正常渲染、环也画出来了。
只有懂这台机器的人看着 "n8n 占 38% 内存" 会觉得不对。

两条对策，缺一不可：
1. 数据层给 `memPct`（已经算好的比例），并在提示词里写死"`memMB: 382` 对应 `memPct: 0.024`"。
2. 仪表渲染改成 `<1%` 而不是 `0%` —— 0.17% 四舍五入成 0，看起来像"这个应用没在跑"。

**每当给模型一个带单位的数，就必须同时给它那个无量纲的版本。** 它不会问，它会自己除。

### 10.4 屏不能越铺越少

系统先铺的兜底屏是"三仪表 + 曲线"，模型随后用 `scene_show` 覆盖时只给了"两仪表 + 曲线"，
磁盘那一格就凭空消失了。用户看到的是**界面在丢东西**，而模型以为自己"重新组织了信息"。

规则进了服务端：新屏的 layer 数少于当前屏、且没有新增问题或结论时，判为重复并要求它
要么给更多、要么别动。和"几何不给模型""时序由前端强制"是同一类：**屏幕的连续性
不该由一次采样决定**。

顺带，`scene_show` 现在默认继承上一屏的曲线。模型只想换个 reading，参数里没有 `trend`，
曲线就整层消失 —— 比一开始就没有更糟，它像是界面在丢东西。

### 10.5 应用列表不是一个仪表

"我装了哪些应用"在真机上答出来是 3 个（n8n、navidrome、qbittorrent）——
系统组件（prometheus 787Mi、citus 398Mi、files 308Mi）不算"用户装的应用"，
虽然它们才是吃内存的大头。

这个区分必须做在数据层（`role: 'app' | 'system'`，靠"有没有自己专属的
`<app>-<user>` 命名空间"判断），不能指望模型从 12 个 pod 里自己挑出 3 个。
用户问"装了什么"时看到 12 个东西会困惑：他心里只有三个。

而且**答这类问题不需要四个仪表**。兜底屏在没有节点读数、只有应用列表时，
用每个应用的 `memPct` 做三个环（环大=占得多，标签=应用名）——这是现有六个编码器里
唯一能表达"多个东西各自多少"的形状。**不完美，但它比"屏幕上什么都没有"好。**

## 11. agent 不是页面，是桌面的一层（2026-10-21）

前面的 agent 一直是个独立页：它自己 `new Field()`，一片粒子、一套 WebGL。
接入桌面时这个结构立刻不成立了 —— 同一块屏上两套粒子，用户还要"从桌面跳到
另一个世界"去跟它说话。而它本来就是这个桌面的管家。

### 11.1 一个场，或者没有场

`shell/src/deskagent.js` 只接收桌面的 `field`，不建自己的：

| 动作 | 场上发生了什么 |
|---|---|
| 唤出 | `slotBegin` 接管那 6400 颗环境粒子；相干度压到 0.34，再回升到 1 |
| 收起 | `clearDraw`，点按 1.6s 的回落散回球面，桌面接手 |

这不是"打开一个面板"，是**同一批粒子改变了自己的说法**。所以唤出的过程不需要
转场动画 —— 相干度先降后升，本身就是"桌面正在变成它"。

环境球的环境点亮度（`dim`）从 0.97 降到 **0.84**。0.97 时桌面球和场一样亮，
两套点阵叠在一起，分不清哪层是界面。

这个值一开始给的 0.62，理由是"球退成很淡的底噪"。**不够**：`dim` 乘的是每颗点的
alpha，而球是加法混合、球心方向上叠着上千颗，0.38 的残余亮度加起来仍然是一片星尘；
读数"45%"又正好落在球心那片密点里，看起来像**透过一层雾在看字**。0.84（残余 0.16）
之后才是设计想要的那句话：桌面没走，但这一屏只有场是亮的。

### 11.2 入口：不出现按钮

桌面平时一个字都没有，所以 agent 的入口也不能是按钮。两条：

- **贴到底边**：`setWells` 在底边放一个很弱的势阱（r=320, k=210），
  粒子被吸下去一点；同时底边亮起一道 3px 的光缝（中间有光核、两端化开）。
  这是暗示，不是控件。点击或按住往上拖 44px，场才真的展开。
- **双击空白**：落在窗口、应用栏、图标上的双击不触发；空白处没有别的含义。

Esc 收起，且**优先于关窗口** —— 用户按下 Esc 时想退出的是"眼前这一层"，
不是背后的应用。

为什么不做"鼠标一碰底边就展开"：底边是浏览器里最容易被路过的区域，
Rail 那种"贴边即开"在左边成立，在底边会变成误触。

### 11.3 交接：三件事都得有人负责

从桌面切到场，有三层东西要同时让位，漏掉哪一层都会露馅：

| 层 | 做法 | 漏掉会怎样 |
|---|---|---|
| 指针 | `field.uiLock` + `GestureTracker.enabled` | 拖仪表时球也在转，两个东西同时响应同一只手 |
| 画布 | `field.rimTo = 0`（窗口边缘粒子） | 窗口的粒子边框还在，agent 像被关在一个框里 |
| DOM | `#windows { opacity: 0 }` | 白边框剩 5% 也看得出一个框 |

窗口的 opacity 一开始给的 0.05，想保留"窗口还在那儿"的暗示。但 `.win` 的边框是
`rgba(228,238,255,.9)` 的实线，乘 0.05 之后在暗背景上依然是清晰的一圈 ——
暗示变成了"囚笼"。归 0，收起时再淡回来。

`rimDim` 是这次给 `field` 加的：窗口边框那圈粒子在 `step()` 里按
`alpha = baseA × dimK × heat × rimDim` 算，rimDim 从 1 平滑到 0。
**并且要吸附**：指数收敛永远差最后一口气（0.002），单颗看不见，
但窗口四角挤着几百颗，加法混合叠起来就是一道看得见的框。这一层要么在，要么彻底不在。

### 11.4 它住在哪个地址

agent 成了桌面的一层，**就没有自己的地址了**。用户端只有一个 URL：

```
https://desktop.<olaresId>.olares.com      ← 桌面本身（= agent 的入口）
```

`/agent/` 是**接口的挂载点**，不是入口。它存在的唯一理由是让 agent 的
`/api/send`、`/api/events` 不和官方 `olares-app` 的 `/api/*` 抢路径 ——
壳层 nginx 把整段前缀原样转给 agent pod（前缀不剥，agent 自己认）。

这里踩过一次：`deskagent.js` 里原本写的是相对路径 `api/send`。
相对路径只对"页面正好挂在 `/agent/` 下面"成立（调试页 `agent.html` 就是），
而桌面在 `/`，于是浏览器把它解析成 `/api/send`，被壳层反代回官方 pod，
拿到 404 —— EventSource 无限重连，屏幕上场是展开了，但永远停在 connecting，
且**控制台不报错**。改成根绝对路径 `/agent/api/*`，谁站在哪一层都对。

同理，`bbbigdan.olares.com`（不带 `desktop.`）是 Olares 的门户，不是这个桌面。

### 11.5 两个"不报错"的 bug

**① 上一屏的化石。** `slotBegin()` 原来只 `drawUse.fill(0)` —— 那只是
"这张工牌作废"，而点的 alpha 还停在旧值，换场之后没有任何人再负责写回去。
症状：开着窗口唤出 agent，窗口边缘残留一圈旧点。修法不是置 0（那会让球面凹一块），
而是**交还环境**：恢复成 `baseA/baseS`，让它们重新成为背景的一部分。

**② 字体里没有那个字。** 曲线的峰值标注原来写 `峰68%`，但那个 `ParticleText`
用的是 `FONT_LAT`（Bahnschrift）—— **它没有中文字形**，浏览器回退到别的字体，
采样出来是另一个字（实测显示成"故43%"）。这类错误不会抛异常，字形永远是"合法"的。
中文只能用 `FONT`（等线），数字才用 `FONT_LAT`；混用的地方要么换字体，要么只写数字。

顺带一条：同一行文字里混排中英文时，**两个字体族的 advance 不一样**，居中对齐会偏。

### 11.6 已知问题

开着窗口唤出 agent 时，画布边缘仍能看到极淡的旧点（11.4 ① 的残留，
`slotBegin` 的交还只恢复了亮度，位置还停在原处等弹簧拉回去）。
主场景（不先开窗口）没有这个现象。试过给 `#scene` 加径向遮罩，
但遮罩会把底部那一行读数一起压暗 —— 代价不对等，撤了。

## 12. 让动作有"风"（2026-10-21）

前面缺了一件很基本的事：**用户按下回车之后，屏幕上没有任何"我收到了"的动作。**
当时的处理只是——字消失、相干度降到 0.58、整个场散成一团云。可那两件事都是
**场自己的状态**，不是对用户动作的回应。看起来像"画面自己糊了"，不像"话被拿走了"。

### 12.1 两套力，两种寿命

`field.setWells()` 是"此刻被谁吸引"，它每帧被整表重写（光标一动就换一批）。
所以它不能拿来表示"我起的这一下"——实测现象是：涡加上去，鼠标一划过就没了。

于是 `field` 多了一张表 `vorts`：一次性切向力，按 `ms` 自己衰减，谁也别擦。
两个用法：

| 时机 | 参数 | 看到什么 |
|---|---|---|
| 按下回车 | `k=2100, swirl=2.9, r=300+26×字数, ms=950` | 整片被卷着往下拽，句子从右往左被吃掉 |
| 在想（每一步） | `k=240, swirl=1.5, r=1250, ms=6000` | 云慢慢旋，不是"糊着不动" |

力乘在**加速度**上而不是位移上：力退到 0 之后点还带着速度继续走，再被弹簧收回来。
余韵来自这里；直接改位移就没有后面那半段。

半径跟着句子长度走。三个字的"嗯？"配 r=620 的涡，看起来像爆炸 —— 力度要配得上内容。

### 12.2 记录：唯一有意不做成粒子的东西

场里只有一行，新的一句会把旧的顶掉。用户想回头看一眼"刚才它到底怎么说"，
界面上没有任何地方可看。所以有了"记录"：

- **服务端**：会话里多一份 `log`（`{r:'u'|'i'|'a', t, ts}`，最多 40 条），
  落盘、随 `resume` 回传，另有 `GET /agent/api/history?sid=` 单独取。
- **前端**：底部右侧一个 `↑ 记录` 的**字**（不是图标——这一层不出现按钮的图形），
  或输入框空着时按 ↑。最多看最近 10 条。
- **它是 DOM，不是粒子**：点阵里中文要 ~30px 才认得出（登录页那一课的结论），
  13px 汉字点阵必然糊成一团，而记录的全部价值就是"能读"。
  所以它是这片界面里唯一一段真正的文字——没有框、没有气泡，只有一层雾。

打开记录时，场不是撤掉，是被**推到后面**：`field.uiFade` 0.1（约 0.3s 到位）。
两样东西叠在一起时，谁都不该被另一个"关掉"——用户只是回头看一眼，
不是离开这一屏。Esc 也分了级：**先收记录，再收这一层**。

一个诚实的取舍：`log` 记的是"说出口的话"。一轮里模型可能先说一句、被兜底句顶掉，
两条都会留在记录里（时间戳相差几十毫秒）。没有做合并——那需要判断"哪句才算数"，
而判断错了比多留一条更糟。
